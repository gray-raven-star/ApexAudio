# 需要时才做代码分析

代码分析用于回答资源、模块、导出和现有接口仍未解决的具体问题。它不是新游戏的默认第一步，不要求 REA，也不要求任何 AI 专用插件。Ghidra、反汇编工具或调试器只是不同工具入口。

## 进入条件

先完成 [调查流程](investigation.md)，然后在笔记中写清：

- 已经检查什么，缺的是哪个接口、对象来源或线程条件。
- 相关的模块、字符串、导出、调用者或数据引用在哪里。
- 本轮要回答的一个问题，以及什么观察可以支持或否定候选。

“没搜到 Wwise”“没有裸 BNK”“接口连接失败”本身不满足这些条件。应先检查实际模块、资源格式、错误阶段和游戏是否正在发声。没有候选时，可以做有限的字符串、导入或交叉引用检索建立候选，不能立即启动所有分析器。

## 从低成本操作开始

1. 已有导出能覆盖现有后端时，核对签名和实际行为，直接复用，不为完善报告而反编译。
2. 已有地址时先读取有限代码，核对 RVA、模块基址、函数入口和调用点。tools/Disassemble.py 可在安装 Capstone 后解码小段 x64 代码；它不会恢复 C++ 对象类型。
3. 需要调用关系或对象结构时，再使用 Ghidra 等工具分析相关函数。记下工具版本、输入文件摘要、分析地址和仍不确定的类型。
4. 每次只取相关引用和函数。反编译得到的猜测类型、参数和函数名都不是最终接口定义，仍需结合调用者和运行时数据核对。

不要把反编译器显示的 void* 或 int 当成已确认的真实 C++ 类型。代码地址、对象实例、所属模块、虚表顺序和线程要求分别确认。

## 控制首次分析成本

对大程序先设置一次调查的范围和等待上限；例如先给候选导入或分析 3～5 分钟的观察窗口，而不是固定反复等满。到时检查实际阶段、进程身份与数据库状态，再决定继续还是缩小范围。这个时间是开发安排，不是兼容性结论。

Ghidra 的首次导入可能启动全程序自动分析。若当前任务只需已知候选，可选择不做自动分析，按限定地址范围解码与反编译。代价是函数边界、类型、间接引用可能不完整，不能把未分析区域当成不存在。

保留自己的研究数据库，后续复用已导入的程序；不要每查一个函数就重新导入 EXE。命令行可参考当前安装版本的 analyzeHeadless 帮助，已有项目通常用 -process 和 -noanalysis 执行小范围脚本。先确认旧进程已结束，避免两份工具写同一数据库。

Windows x64 的 .pdata 条目可能是函数分段，不总是完整函数边界。字节相对位移搜索只能产生引用候选，需实际解码指令验证。未全局分析的数据库可能没有完整指令列表，按需处理指定范围。

## 静态结果怎样落到运行时

分析 VA、RVA、文件偏移、运行时地址要明确标注。运行时模块地址通常是基址加 RVA；堆对象不是模块 RVA，必须经已验证的指针链或 API 取得。

先只读检查候选，再进行目标允许的调用或注册。注册可能只是将请求加入队列；必须确认实际完成、参数内存在完成前仍有效、回调对象生命周期正确。安装采集器与只读分析是不同阶段，不自动关闭保护或修改启动器。

静态分析可帮助找到正确入口，不能证明已经得到 PCM。最终仍按 [验证说明](validation.md)观察真实数据。已有导出足够时完全可以跳过本文，省下工具安装和长时间分析。
